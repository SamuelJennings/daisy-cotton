# Tasks: Core form controls

**Input**: `specs/009-form-controls/` — spec.md, plan.md, research.md, decisions.md

**Organization**: by user story, in build order (plan.md "Story order").

**Every story's done-check**: its acceptance scenarios each have a test that fails when the behaviour is removed, except the gallery and in-browser scenarios the browser check covers (T013). An unknown `variant` and `size` emit no modifier class and do not raise. Its templates pass `uv run python manage.py cotton_lint --warnings-as-errors` (SC-002). Its component, rendered from a caller string, emits no `<script>` and no `on*=` attribute (FR-005, SC-003, `tests/test_form_controls_no_script.py`) and no class daisyUI does not define for it. No component sets `aria-invalid` or an error class on its own (FR-006): one test per control renders it with no `variant` and no `aria-invalid` and asserts neither appears. Each component merges `class` into the root and passes an extra attribute to the element the plan names (FR-002). Every declared name has a default, and one test per component renders it with the names it declares in the surrounding template context and asserts the component's own default (research R4). No wording is asserted. Its new test modules are in `[tool.forge.conformance] non-mirror-paths`. Its README and CHANGELOG lines are written. Every control it adds to the fieldset composition has an accessible name, and colours come from the semantic palette only (FR-004, SC-003).

Tests render through the Cotton compiler as a caller's template would (the `cotton_render_string` and `cotton_render_string_soup` fixtures in `tests/conftest.py`), never by rendering the component file directly.
